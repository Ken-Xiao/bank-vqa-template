# 数据先行入口工作流设计说明

## 目标

把当前“报告功能入口优先”的工作台，调整为“先完成数据对标，再进入报告分析”的两段式流程。用户进入首页后不再先面对报告、口径表单或多个平行入口，而是先进入数据对标，完成目标银行、对标组、年份、角色视角和核心指标域的选择，再把这些选择沉淀为报告可消费的证据包。

本次设计的核心原则是：报告不是独立起点，而是数据对标后的分析出口。

## 当前上下文

当前产品已经具备以下基础：

- `index.html` 已有首页入口面板 `entryDecisionPanel`。
- `js/42-portal-router.js` 已有一等页面路由，当前顺序仍以 `launch` 为第一页面，`benchmark` 位于后段。
- `js/55-benchmark-page.js` 已提供 9 个数据域、核心指标卡、同业对标和因果链拆解。
- `js/56-benchmark-state-bridge.js` 已有对标页到报告页的附录桥接能力，例如 `benchmarkReportAppendixBody`。
- 角色意图已经通过 `benchmarkiq.entryRole` 和 `benchmarkiq.audience` 持久化，为按角色设置对标默认视角提供了基础。

因此，本次改造不重写数据引擎，也不新建第二套路由系统，而是在现有路由、入口面板和对标到报告桥接能力上调整主路径。

## 入口模型

首页入口改为一个强制数据先行的工作流：

1. `数据对标` 是默认第一站。
2. `报告工作室` 是第二站，默认读取数据对标形成的证据包。
3. 角色入口不再绕过数据对标，而是作为数据对标的预设视角。
4. 首页保留轻量说明和必要的目标银行上下文，但不再把报告入口作为并列主入口。

### 主路径

- 首页默认 CTA：`开始数据对标`
- 点击后进入 `benchmark`
- 用户在 `benchmark` 中选择银行、对标组、年份、指标域和故事线
- 系统形成 `对标证据包`
- 用户进入 `report`
- 报告页读取证据包，生成或展示“结合数据的报告分析”

### 角色路径

角色入口仍然保留，但全部进入 `benchmark`，只改变默认视角：

- `董事会 / 行长室`：默认关注 ROE、规模、资本回报、核心结论和经营优先级。
- `CFO / 财务`：默认关注 NIM、存款成本、资产负债结构、收入拆解和分解公式。
- `CRO / 风控`：默认关注不良、拨备、逾期、对公风险、零售风险和 IFRS9。
- `研究 / 专家`：默认关注全指标、数据口径、证据链、字段覆盖和可复核路径。

角色入口点击后写入 `benchmarkiq.entryRole` 和 `benchmarkiq.audience`，并路由到 `benchmark`。对标页根据该值设置默认 tab、指标域、卡片排序和提示文案。

## 对标证据包

新增一个轻量的概念模型：`Benchmark Evidence Pack`，中文名为 `对标证据包`。

证据包不是新的大型数据仓库，而是对用户在数据对标页中形成的分析选择做结构化记录。建议初始字段如下：

- `bankId`：目标银行。
- `peerGroupId`：对标组。
- `year`：分析年份。
- `audience`：角色视角。
- `selectedDomains`：已重点查看的数据域。
- `selectedMetrics`：已加入报告的核心指标。
- `causalChains`：已确认的跨域因果链。
- `storyCards`：已加入报告的故事线卡片。
- `updatedAt`：最近更新时间。

第一期可以把证据包存在 `localStorage`，使用 `benchmarkiq.evidencePack` 作为 key。后续如果接入后端或项目文件，可以把该结构迁移为可保存、可导出、可复用的分析状态。

## 报告页规则

报告页应从“空白报告入口”改为“数据证据驱动的报告工作室”。

当证据包为空时：

- 报告页仍然可以打开，避免首页卡住。
- 页面顶部显示明确提示：`请先完成数据对标，报告将基于对标证据生成分析。`
- 主 CTA 指向 `benchmark`。
- 不隐藏报告功能，但默认不生成看似完整却没有数据依据的分析。

当证据包存在时：

- 报告页顶部展示本次分析口径：目标银行、对标组、年份、角色视角。
- 报告正文或附录区展示来自数据对标的关键发现。
- 已加入报告的指标、故事线和因果链进入报告分析区。
- `benchmarkReportAppendixBody` 从“附录补充”升级为“报告证据区”的一部分。

## 路由与导航

推荐把业务页面顺序调整为：

1. `benchmark`：数据对标
2. `answer`：结论摘要
3. `evidence`：证据地图
4. `topics`：专题归因
5. `report`：报告工作室
6. `data`：数据复核

`launch` 可以保留为轻量首页或欢迎层，但不应再是用户的第一业务步骤。首次加载时，如果没有明确 hash 或已恢复页面，默认进入 `benchmark`。

左侧 Page Rail 的命名应同步改为数据先行语言：

- `数据对标`
- `结论摘要`
- `证据地图`
- `专题归因`
- `报告工作室`
- `数据复核`

## 首页改造

首页入口面板应表达一个清晰顺序：

- 第一块：`先做数据对标`
- 第二块：`再进入报告分析`
- 第三块：`选择你的角色视角`

报告入口不再作为与数据入口并列的主按钮，而是作为第二阶段说明和辅助链接存在。首页文案应避免让用户误解为可以先写报告、再找数据补充。

首页不会因为强制数据先行而卡住，因为：

- 默认 CTA 直接进入 `benchmark`。
- `benchmark` 页已有可浏览的默认数据状态。
- 报告页仍可打开，只是在没有证据包时提示用户先完成对标。

## 成功标准

- 首次进入产品时，默认业务入口是 `benchmark`。
- 首页首屏明确表达“先数据对标，再报告分析”。
- 四个角色入口都进入 `benchmark`，并写入角色视角。
- 报告页在没有证据包时不生成空洞分析，而是提示回到数据对标。
- 报告页在有证据包时展示对标口径和关键证据。
- 现有 9 个数据域、因果链和报告附录桥接能力继续可用。
- 契约测试覆盖默认路由、入口卡片、角色入口、证据包空态和报告页桥接。

## 非目标

- 不在本期新建完整后端状态管理。
- 不重写 `js/55-benchmark-page.js` 的指标计算逻辑。
- 不把报告页做成强制 wizard。
- 不删除现有 `launch`，只降低其业务入口权重。
- 不改变现有数据文件结构。

## 风险与处理

- 风险：强制数据先行可能让想直接看报告的用户觉得路径变长。处理方式：报告页可打开，但明确显示数据证据缺失，并提供回到对标的 CTA。
- 风险：证据包第一期使用 `localStorage`，跨设备不可复用。处理方式：先把数据结构设计清楚，后续再迁移到项目文件或后端状态。
- 风险：角色入口全部进入对标页后，原有董事会 / 风控快速入口心智会变化。处理方式：用角色预设减少二次选择，进入后直接看到相关指标域。
- 风险：Page Rail 和首页语言不同步会造成混乱。处理方式：本期同步修改路由标签、摘要和首页文案。

## 建议实施顺序

第一期只做主路径闭环：

1. 契约测试：默认入口为 `benchmark`，角色入口全部指向 `benchmark`。
2. 路由调整：首次加载默认到数据对标，Page Rail 顺序调整为数据先行。
3. 首页改造：首页文案和卡片顺序改为“先对标、再报告、按角色预设”。
4. 证据包空态：报告页识别是否存在 `benchmarkiq.evidencePack`。
5. 报告桥接：复用现有 `benchmarkReportAppendixBody`，展示证据包摘要。
6. 验证：运行入口、路由、对标桥接相关 contract tests。

第二期再增强分析深度：

1. 对标页支持一键生成证据包。
2. 跨域因果链进入报告正文。
3. 角色预设影响指标排序和默认故事线。
4. 报告页按董事会 / CFO / CRO / 专家视角生成不同结构。
