# 数据资产与管理层报告工作台设计说明

## 1. 背景与问题

当前平台已经完成“先数据对标，再报告分析”的主流程，但进入结论摘要、证据地图、专题归因后，页面内容仍然偏多、偏散，容易出现三个问题：

1. 结论摘要像是把所有发现压缩到一页，缺少管理层最关心的主判断。
2. 证据地图既想解释结论，又想列证据，还想承载图表入口，导致角色不清。
3. 专题归因同时展开太多链条，用户很难判断哪些内容应该进入最终报告。

下一阶段不应继续往页面里加组件，而应把平台重心调整为“数据资产生成可信诊断包，报告工作台基于诊断包生成候选 PPT 页”。

## 2. 产品定位

平台下一阶段定位为：

> 数据资产驱动的管理层诊断与报告生成工作台。

它不是一次性自动生成完整报告，而是先形成一组有主次的管理层诊断判断，再将每个判断展开成可选择、可审稿、可放入最终报告的候选页面。

## 3. 目标体验

用户完成目标银行、对标银行、分析年份、身份选择后，平台应形成一个闭环：

1. 数据资产页生成“本轮管理层诊断包”。
2. 结论摘要只展示 3 个核心管理层判断。
3. 证据地图验证这些判断是否有足够证据支撑。
4. 专题归因只展开 1-3 条最强因果链。
5. 报告页库自动生成候选 PPT 页，用户选择是否放入最终报告。

用户感受到的不是“系统列了很多内容”，而是“系统帮我判断了最值得讲什么，并把证据和页面准备好了”。

## 4. 信息架构调整

### 4.1 数据资产页

数据资产页从“指标展示页”升级为“诊断输入页”。它负责生成并解释诊断包，不负责写报告正文。

页面只保留四类高权重信息：

- 本轮口径：目标银行、对标组、年份、身份。
- 核心差距：最多 8-12 个关键指标。
- 主要问题域：盈利、负债、资产质量、资本、流动性等自动排序。
- 可用证据：图表、指标、因果链、数据质量状态。

超出高权重范围的指标进入“指标库/展开层”，不直接占用主视图。

### 4.2 结论摘要

结论摘要只回答一个问题：

> 这家银行当前最需要管理层关注的 3 个判断是什么？

固定结构为：

- 总判断：一句话说明经营质量状态。
- 判断一：最主要压力。
- 判断二：最主要原因。
- 判断三：最优先动作。

每个判断最多展示：

- 一句结论。
- 一个核心指标差距。
- 一条因果链。
- 一个进入候选报告页的入口。

其他指标、口径解释、次级证据全部折叠到“展开证据”。

### 4.3 证据地图

证据地图从“正文解释页”改成“审稿索引页”。它只回答：

> 这些管理层判断有没有足够证据支撑？

推荐结构：

- 左侧：3 个管理层判断。
- 中间：每个判断绑定的指标、图表、因果链。
- 右侧：数据质量、口径提示、是否可入报告。
- 底部：生成候选报告页、降级为附录、要求补数。

证据地图的文字应尽量短，重点放在“证据是否够硬”和“能否进入报告”。

### 4.4 专题归因

专题归因只回答：

> 哪 1-3 条因果链最值得展开讲？

每条因果链是一组固定故事页：

1. 问题页：核心异常是什么。
2. 直接原因页：哪个指标直接解释异常。
3. 深层原因页：结构性原因是什么。
4. 管理动作页：下一步应该做什么。

示例：

```text
ROE 偏低
→ 净息差低于对标组
→ 存款定期化率偏高、负债成本压力偏大
→ 调整负债结构、优化高成本存款占比
```

专题归因不再同时铺开所有专题。未进入前 3 的专题降级到“备选专题”。

### 4.5 报告页库

报告页库兼顾报告生成器能力，但不追求一次性生成整本报告。

每个管理层判断和专题链条自动生成候选 PPT 页。用户可以：

- 加入最终报告。
- 作为附录。
- 重新生成。
- 删除。
- 调整顺序。

最终报告由用户挑选候选页组成，系统负责提供高质量候选，不替用户一次性塞满。

## 5. 管理层诊断包数据结构

新增或统一一个前端数据结构：`managementDiagnosisPack`。

建议字段：

```js
{
  context: {
    targetBank,
    peerBanks,
    year,
    role
  },
  executiveAnswer: {
    headline,
    totalVerdict,
    priorityJudgments: []
  },
  judgments: [
    {
      id,
      title,
      conclusion,
      severity,
      primaryMetric,
      metricGap,
      causeChain,
      evidenceRefs,
      recommendedAction,
      reportPageRefs
    }
  ],
  evidenceMap: [
    {
      judgmentId,
      evidenceType,
      metricKey,
      chartType,
      dataQuality,
      reportReadiness
    }
  ],
  topicChains: [
    {
      id,
      title,
      priority,
      nodes,
      pages
    }
  ],
  candidatePages: [
    {
      id,
      sourceType,
      sourceId,
      title,
      pageRole,
      status
    }
  ]
}
```

三类页面都读取同一个诊断包，避免各自从原始数据里重新拼内容，导致判断不一致。

## 6. 页面生成规则

### 6.1 判断优先级

管理层判断优先级由四类信号共同决定：

- 差距强度：目标银行相对对标组偏离程度。
- 业务重要性：该指标是否影响经营质量主线。
- 因果完整度：是否能形成至少两层原因链。
- 数据可信度：指标口径和数据质量是否足够进入报告。

### 6.2 页面数量控制

默认控制：

- 结论摘要：1 组总览 + 3 个判断。
- 证据地图：3 个判断对应的证据索引。
- 专题归因：1-3 条链，每条 2-4 页。
- 候选报告页：默认 6-10 页，不超过 12 页。

这样可以避免平台再次回到“内容越多越像完整”的误区。

### 6.3 文案规则

文案遵循管理层汇报口径：

- 先说判断，再说证据。
- 少用泛化形容词，多用指标差距。
- 每页只保留一个主判断。
- 解释链条必须可追溯到证据包。
- 没有证据支撑的内容只能进入“待复核”，不能进入正式报告页。

## 7. 交互流程

```text
首页选择口径
→ 数据对标
→ 生成管理层诊断包
→ 查看 3 个核心判断
→ 进入证据地图复核证据
→ 选择 1-3 条专题链
→ 生成候选报告页
→ 勾选进入最终报告
```

用户可以从任意候选报告页跳回：

- 对应判断。
- 对应证据。
- 对应专题链。
- 原始指标口径。

这种跳回能力是后续审稿和修改的关键。

## 8. 错误与空状态

当证据不足时，不应生成表面化结论。

推荐状态：

- 指标缺失：显示“该判断暂不进入核心结论，需补充指标”。
- 对标组不足：显示“对标样本不足，建议补充同类型银行”。
- 因果链不足：显示“只能形成单点差距，暂不生成专题页”。
- 数据质量低：显示“可作为线索，不建议进入正式报告”。

## 9. 分阶段实施

### 阶段一：三页瘦身

重构结论摘要、证据地图、专题归因的信息层级。

目标：

- 每页主视图只承载一个明确任务。
- 次级证据全部进入展开层。
- 页面不再同时展示过多卡片、列表和解释文字。

### 阶段二：统一诊断包

新增 `managementDiagnosisPack` 生成逻辑。

目标：

- 三页共用同一个判断源。
- 3 个核心判断、证据索引、专题链条保持一致。
- 报告页库从诊断包读取页面候选。

### 阶段三：候选报告页库

把每个判断和专题链条转成候选 PPT 页。

目标：

- 用户可以勾选、排序、删除、重新生成。
- 每页能跳回证据和原始指标。
- 最终报告只由用户确认过的页面组成。

### 阶段四：数据资产治理增强

补充指标口径、数据质量、指标血缘和图表资产管理。

目标：

- 平台能解释“为什么这个指标可信”。
- 报告页能自动带出口径说明。
- 数据质量不足时阻止弱结论进入正式报告。

## 10. 成功标准

本次改造成功的判断标准：

1. 用户进入结论摘要后，10 秒内能看懂 3 个核心判断。
2. 每个判断都能追溯到指标、图表和因果链。
3. 证据地图不再像正文页，而是像审稿控制台。
4. 专题归因默认只展示最强 1-3 条链。
5. 候选报告页默认不超过 12 页。
6. 用户可以清楚决定哪些页进入最终报告。

## 11. 非目标

本阶段不做：

- 一次性全自动生成完整报告。
- 大规模后端数据仓库重构。
- 新增复杂权限体系。
- 新增多用户协作。
- 把所有指标都做成主视图。

这些可以作为后续平台化阶段处理。
